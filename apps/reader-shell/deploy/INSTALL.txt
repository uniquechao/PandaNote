Why the entry is not an invented /overlay boot hook
rcS first picks /opt/script or fallback /opt_orig/script and backgrounds start_qpe.
Stock start_qpe then mounts overlay (/opt_orig lower, /overlay/system upper -> /opt)
and runs install_product, which can format /home. p5 /script -> opt/script and
/image -> opt/image. p4 upper /system/opt/script is absent in the acquired snapshot.
An upper-only replacement may be invisible at the initial rcS dispatch. Do not
run stock initialization to obtain a convenient boot path. qpeentry's internal
supervision is unverified; a bounded normal-boot supervisor must be reviewed and
physically tested before a new rcS hash can be frozen. RAM PID1 is not that proof.

No verification CLI accepts self-asserted hardware proof. The Python verify_clone
API accepts all five clone-only checks (display, touch, calendar, offline, stable)

true changes only the local journal to clone-verified. It executes no program.

Transaction and recovery
1. Validate detached canonical manifest, worktree/clone identity, exact destination
   paths, source hashes, old destination hashes/modes; hold exclusive clone lock.
2. Before any target write, fsync persistent old files and same verified manifest.
   The manifest SHA is the transaction identity. Never reuse/replace another old
   payload: deploy to a fresh version path. Preserve the complete old rcS + mode.
3. Fsync and atomically rename payload files first, then journal switching-entry,
   then fsync/atomic-rename rcS, then journal awaiting-verification.
4. A crash at any journalled step means recover before another install. Rollback
   validates every old backup and all current target hashes first, restores entry
   first, removes only explicitly listed newly created candidate files, fsyncs
   each parent, and retains all old backups. Repeated rollback is safe.
5. Missing/corrupt backup or unknown current bytes: stop without overwriting the
   entry. Restore verified backup bytes AND original modes from trusted retained
   source, or inspect separately. Do not delete journal or backup to bypass it.
6. Recovery interruption: rerun rollback with the identical canonical manifest;
   current files may be old or new, but an unknown third version always stops.

Crash model and limitations
The write-ahead journal and fsync/rename protect sequential process interruptions
in a non-hostile exclusive local clone. Tests include os._exit after entry switch.
This is not a general adversarial-filesystem sandbox, signed-update trust root,
normal-boot supervisor, or proof of eMMC/cache behavior under power loss. Exact
manifest identity is not cryptographic authenticity; review supplies provenance.
Temporary .<filename>-* files can survive abrupt termination; they are not active
entry files. Do not recursively delete backups/versions while recovering.
