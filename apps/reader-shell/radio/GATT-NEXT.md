# Controller-owned LE capability / iPhone provisioning next checkpoint

This is an implementation/probe proposal, not a completed feature. Wi-Fi checkpoint can be reviewed independently.

1. Keep the current mem=64M capsule/guard exclusions unchanged. Use the already reviewed radio-first low-memory boot candidate before staging Qt/fonts. Freshly recheck root ro+norecovery, disk RO, swap, listener and wlan0-only guard; do not run original startup/stop scripts.
2. Read controller identity before deciding mode: exact AIC module/firmware hashes, ttyS3 ownership, rfkill names/states, initialized hci0 `hciconfig -a` features and HCI `Read Local Supported Features`/`Read Local Version` response. Controller runs a bounded original tool only after its source/hash/static audit; tools themselves are not proof of feature support. Query LE support bit from controller response and compare Linux management supported_settings LE flag. Neither stock bredr config nor files named AIC8800 prove absence/presence of usable LE peripheral mode.
3. Before launching bluetoothd, inspect its exact build/version/options, storage-dir compiled strings, and shared library dependencies offline. Stock storage commonly resolves `/var/lib/bluetooth`; a private D-Bus address alone does not redirect this. A reviewed build with explicit volatile storage or proven existing tmpfs symlink path is required. Do not remount root or add bind mounts silently: PID1 mount guard would reject extra mounts and persistent pairing files are prohibited.
4. Use one private D-Bus socket under `/tmp/pandanote-connectivity/dbus/` with an explicit own-process config (no system service activation, no public bus). Run owned bluetoothd with reviewed `ControllerMode=dual` only if LE supported; no BlueALSA. Registration must confirm org.bluez.GattManager1 and LEAdvertisingManager1 on the actual adapter; those APIs plus successful RegisterApplication/RegisterAdvertisement establish usable server plumbing, not phone service acceptance.
5. Implement a separate bounded GATT service/agent using an available audited runtime/library: stock firmware inventory includes dbus/gdbus tools but no established Python+dbus service runtime or cross-linkable libdbus/glib headers. A sustained agent must own discovery and confirmation requests, publish numeric comparison in native UI, support timeout/cancel, and reject unsolicited peers. `bluetoothctl pair` with no UI agent does not satisfy this.
6. GATT application proposal: one custom service with Status read/notify, Provision write (framed schema/SSID/password, bounded size, session nonce, credentials never logged), Control write (allowlisted actions only), TransferControl read/write and TransferChunk write/notify. File reception uses bounded chunking, per-session file name allowlist, announced length/sha256, offset sequencing, tmpfs quota, atomic finalization and cancel cleanup. No arbitrary paths, shell execution or direct persistent storage. Provision and file writes require a local device confirmation plus authenticated/encrypted connection; a plain unauthenticated BLE characteristic would expose Wi-Fi secrets.
7. iPhone needs a real compatible CoreBluetooth client for the custom protocol. CoreBluetooth central must discover service/characteristics, handle MTU/chunked file transport and the device confirmation handshake. Generic iOS pairing, Files/AirDrop and Safari alone cannot be assumed to support arbitrary custom BLE file transfer. CoreBluetooth app/library availability remains a user/product gate. A paired or Connected=yes state is not completion.
8. Acceptance evidence must separately show LE advertising visible to target iPhone; service discovery; approved provisioning over the encrypted/bonded session; Wi-Fi authentication/address and authenticated manager fetch; control acknowledgment; a real book/file sent by phone with byte count+sha256+reader availability; disconnect/reconnect and cancel/error cleanup. No claim can be based on mocks or strings alone.

Next code work should begin with exact stock BlueZ storage path/version evidence and controller's actual LE-supported-settings result. If stock BlueZ cannot be isolated in the existing guard, choose a reviewed temporary replacement build or explicitly bounded guard extension; do not create `bluez-ready` merely because a bus process is running.
